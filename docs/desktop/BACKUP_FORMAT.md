# JRVS Property Co. — Portable Workspace Backup

**Current format:** JRVS Portable Workspace, version 2  
**File extension:** `.jrvsbackup.gz`  
**Container:** GZIP-compressed UTF-8 JSON

## Payload structure

The decompressed JSON contains:

- `format`: `jrvs-portable-workspace` or `jrvs-legacy-workspace`
- `formatVersion`: integer (2 for current exports; version 1 remains importable)
- `appVersion` when generated by the desktop application
- `exportedAt`: ISO-8601 timestamp
- `business`: complete `jrvs-data` object, including unknown fields and numbering state
- `calendar`: complete `jrvs-calendar` array
- `photos`: full photo metadata plus base64-encoded original and optional preview blobs
- `hasPhotoLibrary`: indicates whether restore should reconcile the target photo library to the source backup
- `manifest`: version 2 integrity information

Each version 2 photo includes:

- `originalByteLength` and `originalSha256`
- `previewByteLength` and `previewSha256` when a preview exists
- The original and preview MIME types

The version 2 manifest includes the SHA-256 hashes of the serialized business and calendar payloads, photo count, and aggregate original/preview byte counts. Hashes are lowercase hexadecimal SHA-256 values over the original Blob bytes. Business and calendar hashes are calculated over their JSON string representation.

## Backup behaviour

- The backup is assembled from the SQLite-backed localStorage compatibility store and the photo library's IndexedDB working cache.
- Photo originals are included byte-for-byte and are also mirrored into the native managed photo folder.
- The original browser/PWA data is not changed by export.
- The app downloads the compressed file to the normal Windows download location.
- Version 2 imports validate the business and calendar hashes, photo count, duplicate photo IDs, original byte lengths and per-file SHA-256 hashes before asking to replace the active workspace.
- Version 1 imports remain supported for older JRVS exports, but they do not contain per-file checksums.
- Before replacing business/calendar records, the app downloads a full safety backup. The native importer also keeps a JSON snapshot of the current SQLite key/value store under the workspace backups folder.

## Current limitations and safeguards

- Version 2 improves integrity checking but still uses GZIP-compressed JSON rather than a streaming ZIP container.
- Very large libraries may require substantial memory while blobs are encoded and compressed.
- The restore is a guarded replacement flow, not a fully atomic multi-file workspace swap. Keep the downloaded safety backup until the restored records and several original files have been checked.
- The photo editor continues to use IndexedDB as its active working cache; native managed copies are mirrored separately.
- The first restore flow is designed for a single workspace replacement, not merging two businesses.
- No source browser data is cleared or moved during export.
